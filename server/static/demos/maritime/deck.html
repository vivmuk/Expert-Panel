What the public pages say about Maritime.

Research brief · AI-generated from public pages

For a software team that already has a repository and wants a public web agent, the public pages point to Maritime's "Public web agents" flow: any repo with a Dockerfile at the root can be served on a public, no-login HTTPS URL, and Maritime builds it, runs it serverlessly, sleeps it when idle, and wakes it on the next visit[1]. The documented command is `maritime create my-app --repo https://github.com/you/app --public`, with `--repo`/`--branch` selecting the build and `--public` exposing the URL[1]. So Maritime should host the built container and the public URL, while the team operates the repo, the Dockerfile, and the app's own runtime behavior; the custom-container page frames this as wrapping the agent in a small HTTP server that speaks a two-endpoint contract, and notes that a plain web app with a public URL needs no chat contract[2]. Before deploying, the team needs a Dockerfile at the repo root, a chosen branch, a port to expose (the `--port` flag is listed but its description is truncated in the source, so the exact default is an assumption), and a Maritime account/API key; signup requires Google, GitHub, or email plus verification, and the first machine asks for a card that is not charged during the free trial[3]. The CLI can log in via a browser code or, for CI, skip login and set `MARITIME_TOKEN`[4]. Pricing context: the first 7 days are free with up to $20 of usage[3], and machines are billed per second, with agent boxes at $1/mo per 2 GB[5]. Note that these are public docs; the company did not commission this note.

    07 Synthesis

    What the panel converged on, and what it can't see.

    Synthesis

    The experts converge on a clear hosting split: Maritime should host the public agent runtime, build execution, TLS, sleep/wake, and the public URL, while the team retains the repository, Dockerfile, entrypoint, secrets, and access controls. Before any maritime create --public, the team must land a committed, CI-gated artifact set — a root Dockerfile with pinned base, a declared port and health endpoint, an env/config manifest, and a token stored as a CI secret — with every field tagged confirmed versus assumed against public maritime.sh pages. The plain single-port HTTP server is the baseline; the two-endpoint chat contract is conditional on the agent actually being conversational.

    Key themes
    1. 01Explicit, committed ownership boundary between platform-hosted and team-operated surfaces
    2. 02CI-gated pre-deploy artifact checklist (pinned Dockerfile, port, health endpoint, env manifest, token as secret)
    3. 03Provenance discipline: public pages are evidence, not contract, so assumptions must be labeled
    4. 04Public exposure shifts abuse, cost, and rate-limit controls onto the team's container
    Blind spots
    1. !The --port default and idle-sleep/wake semantics are truncated or silent in public pages, so any port-binding recommendation may rest on an unverified assumption
    2. !Whether Maritime requires a chat message schema versus accepting a plain web app is unresolved, risking adoption of the wrong contract
    3. !Signup, verification, trial-card, and MARITIME_TOKEN issuance mechanics are inferred from the quickstart's visible shape, not confirmed

          13 30 / 60 / 90 rollout and evals · Target = a target, not a result

          30/60/90: what ships when, and how it's tested.

          Days0–30

          Stand up orchestrator, discovery, and repo audit. Ship maritime-deploy-manifest and the manifest lint. Seed the anti-pattern list. Run offline gate fixtures in shadow mode. Target gate fixtures at 100% correct failure.

          Days31–60

          Enable hosting-shape and artifact prep with human checkpoints. Turn on the predeploy gate as a required CI check. Ship maritime-agent-contract and the classifier suite. Begin online smoke and rate limiter probes. Target classifier agreement ≥95%; zero false gate passes.

          Days61–90

          Enable deploy, smoke-test, and operate stages with human sign-off. Turn on QHX delta enforcement and the review cadence. Publish the single provenance-carrying access and artifact page, GitHub-first, with browser-code CLI login for humans and MARITIME_TOKEN for CI. Target 100% of production runs carry a QHX delta; one page replaces the two onboarding documents.

          Offline evals
          • Gate fixture suite: seeded repos with each missing artifact; gate must fail with the correct named reason. Pass criterion 100% of fixtures fail correctly and zero false passes.
          • Contract linter suite: mismatched port, missing health path, chat contract on plain agent. Pass criterion all mismatches flagged.
          • Manifest lint: untagged lines rejected. Pass criterion 100% rejection.
          • Classifier suite: labeled plain vs conversational cases. Target ≥95% agreement with labels.
          Online evals
          • Public smoke on every deploy: GET /health returns 200 and the request route returns the documented shape. Pass criterion both pass before sign-off.
          • Rate limiter probe: burst above threshold returns 429. Pass criterion 429 observed within the documented window.
          • Uptime probe: alert fires within the configured threshold on simulated downtime. Target alert latency under 2 minutes.
          • QHX delta presence: every production run writes exactly one delta. Pass criterion 100% of runs.
